# 아키텍처 개선 대상의 정량화 가능성 측정 (2026-08-10)

「오로라웍스 아키텍처 개선 대상 도출 보고서 v9」의 정성 서술을 **비용처럼 정량적으로** 바꿀 수 있는지
실제로 재본 결과다. 결론부터 적는다.

- 측정 대상: 보고서 v9 원문 + WM 지식그래프(노드 30,336 / 관계 37,759)
- 측정 방법: 보고서 전문 통독 + Neo4j Cypher 직접 조회
- 측정일: 2026-08-10

## 한 줄 결론

**오늘은 정량화할 수 없다. 그리고 그것은 분석이 부실해서가 아니라 측정이 아직 없어서다.**

막힌 곳이 두 겹이다.

1. **보고서 쪽**: 비용으로 바꾸려면 곱셈의 세 항(단가 · 빈도 · 모집단)이 필요한데 세 항이 전부 없다
2. **그래프 쪽**: "문제 → 걸린 금액" 경로가 **구조적으로 0건**이다

## 1. 보고서에 있는 숫자는 두 종류뿐이다

### 언급 횟수

현장 의견 19건 → 검토 항목 25건 → 아키텍처 검토 10건 → 구조 문제 3건.
근거 건수는 A1 7건 · A2 2건 · A3 1건이다. 기능 개선 9건 · 문서 개선 5건 · 판정 보류 1건.

**언급 횟수는 아픔의 크기가 아니다.** 수집 표본에서 몇 번 나왔는지다.
같은 고객이 두 번 말하면 2건이 되고, 말하지 않은 고객은 0건이 된다.

### 제안 기준 사양

서비스 15개 이상 기동 · 서비스 17종 · 주요 서비스 3대 · 8Core 64GB · 재기동 20분 이상 · WAS 3대.

**이 값들은 곱할 상대가 없는 외짝 값이다.** 사양만으로는 부담의 크기를 말할 수 없다.

## 2. 비용으로 바꾸려면 무엇이 필요한가

| 보고서 서술 | 비용 = ? | 있는 항 | 없는 항 |
| --- | --- | --- | --- |
| A1 "점검 때 업무가 중단됩니다" | 재기동 20분 × 연간 횟수 × 영향 인원 | 20분 | **연간 횟수, 영향 인원** |
| A1 "인프라 부담이 커집니다" | 서버 대수 × 대당 단가 × 고객사 수 | 사양(8Core 64GB) | **실제 대수, 단가, 고객사 수** |
| A1 "방화벽 오픈 신청이 너무 많이 필요" | 신청 건수 × 건당 처리 공수 | 없음 | **건수, 공수** |
| A2 "승인이 지연되거나 반려됩니다" | 지연 일수 × 일당 비용 | 반려 사실 1건 | **지연 일수** |
| A2 "버전을 올릴 때마다 다시 손봐야" | 상향 빈도 × 회당 재작업 공수 | 없음 | **빈도, 공수** |
| A3 "정상화가 길어질 수 있습니다" | 발생 건수 × 정상화 시간 | 없음 | **발생 건수(0으로 확인됨), 시간** |
| F1 "고객사 3곳에서 반복" | 3곳 ÷ 전체 고객사 수 | 분자 3 | **분모(전체 고객사 수)** |

**A3 은 특히 중요하다.** 보고서 스스로 세 곳에서 "실제 발생 이력은 아직 확인되지 않았다"고 적었다.
곱셈의 첫 항인 빈도가 없으므로 A3 은 어떤 축으로도 정량화의 출발점이 없다.
빈도가 0으로 확인되면 기대 비용은 0이고, 그때는 정량화가 아니라 **판정 자체가 바뀐다.**

## 3. 보고서가 스스로 표시한 공백 6항목

보고서는 이 공백을 감추지 않고 자기 문서 안에 적어 두었다.

- (A1) 서비스별 실제 자원·DB 연결 사용량
- (A1) 재기동 20분의 구간별 비중, 축소 구성이 성립하는 조건
- (A2) 같은 반려가 반복되는 고객사 수 (수집 중)
- (A2) 해당 저장 형식을 쓰는 기능 전체 목록
- (A3) 실제 불일치·재색인 발생 이력과 정상화 소요 시간
- (H1) 반복 여부

이 여섯 개가 채워지지 않으면 정량화는 열리지 않는다.
그중 **(A2) 저장 형식을 쓰는 기능 목록은 코드로 지금 채웠다** → `통합테스트-실태-2026-08-10.md` §6 (`@Lob` 184곳 · 124파일 · 9모듈).

## 4. 그래프에서 "문제 → 금액" 경로는 0건이다

가장 그럴듯한 정량 축은 "이 문제에 걸려 있는 딜 금액"이었다. 실제로 재보니 닫히지 않는다.

| 측정 | 값 |
| --- | --- |
| `Deal` 노드 | 107건 |
| 그중 `amount_krw` 가 있는 것 | **13건 (12.1%)** |
| 금액 합계 | 34.092억 (won 3건 6.042억 / open 10건 28.05억) |
| `Account` 노드 | 406곳 |
| 그중 `HAS_NEED` 가 붙은 것 | **4곳 (0.99%)** |
| 금액 있는 딜을 가진 `Account` | 12곳 |
| **니즈 있는 계정 ∩ 금액 있는 계정** | **0곳** |
| `Need` → `Account` → `Deal(amount_krw)` 경로 | **0건** |
| 2곳 이상이 공유하는 `Need` 15개의 파이프라인 금액 | **전부 0원** |
| `Need` 와 `Deal` 을 함께 언급하는 `Observation` | **0건** |
| `Need` 와 `Account` 를 함께 언급하는 `Observation` | 130건이지만 계정은 같은 **4곳** |

**이것은 엔티티 정합 실패가 아니다.** `Account.canonical_name` 중복은 0건이라 조인 키는 깨끗하다.

원인은 자료 범위다. **니즈는 구축 고객 4곳의 Pain 대장에서만 뽑혔고, 금액은 영업 파이프라인에서만 뽑혔다.
두 자료가 다루는 고객이 겹치지 않는다.**

- 니즈가 붙은 4곳: 마바손해보험 · 사아캐피탈 · 타하렌터카 · 카파전선
- 금액이 있는 12곳: 바람화재 · 누리손해보험 · 다라카드 · 가나손해보험 · 미리내저축은행 등

보고서 등장 고객사 중 그래프에 금액이 있는 것은 **바람화재 5.08억(수주·won)** 과
**누리손해보험 4.0억(타겟·open)** 둘뿐이고, 마바손해보험·AIA생명은 딜 노드는 있으나 금액이 비어 있다.
따라서 F1 의 "고객사 3곳 반복"조차 금액으로 바꿀 수 없다.

## 5. 그래프에 아예 없는 것

| 무엇 | 상태 |
| --- | --- |
| `Test` 노드 | **0건** (라벨은 예약돼 있음) |
| `VALIDATED_BY` 관계 | **0건** |
| `BLOCKED_BY` 관계 | **0건** — "무엇이 딜을 막고 있나"를 못 묻는다 |
| `CONTRADICTS` 관계 | **0건** — 그런데 `lane=conflict` Claim 이 237건이라 상대편을 못 찾는다 |
| 회사 연 매출 목표 기준값 | 노드·속성 어디에도 없다 |
| 인프라 사양(8Core·서버 대수·재기동 시간) | 구조화된 속성으로 없다 |

연 매출 목표 60억은 `config/criticality-rules.yaml` 32행에 텍스트로만 있다
(목표 6,000,000,000 / 달성 1,745,221,025 / 달성률 0.2909).
그래프 금액 합계 34.092억과 이 달성액 17.45억은 정의가 달라 서로를 재현하지 못한다.

## 6. 지금 그래프로 낼 수 있는 정량 답의 최대치

두 가지뿐이다. 둘 다 단서를 반드시 달아야 한다.

1. **금액이 붙은 딜 13건의 합계와 단계별 교차 집계**
   → 단서: 107건 중 13건의 값이므로 "파이프라인 총액"이 아니다. 나머지 94건을 0원으로 취급한 값이다
2. **고객사가 붙은 관측 3,020건의 계정별·출처별 건수**
   → 단서: 87%가 슬랙 단일 출처라 "사실의 무게"가 아니라 대화량의 대리지표에 가깝다

인과("사양 때문에 실주했다")나 비율("전체 고객사 중 몇 %")을 묻는 질문에는 답을 낼 수 없다.

## 7. 무엇을 하면 열리는가

우선순위 순이다.

1. **니즈 추출을 영업 자료까지 확대한다.** `HAS_NEED` 커버리지 4/406 이 풀리면
   "문제 → 계정 → 금액" 경로가 자동으로 열린다. 엔티티 정합 작업은 필요 없다(키가 깨끗하다)
2. **딜 금액 추출 규칙을 보강한다.** 금액 속성이 아예 없는 딜이 88건이다.
   `amount_raw` 가 `"0"`·`"-"` 인 6건은 원본에 값이 없는 것이고, 나머지는 추출이 안 된 것이다
3. **보고서가 표시한 6항목을 실제로 측정한다.** 그래프가 할 수 있는 일이 아니고 사람이 재야 한다
4. **회사 기준값(연 매출 목표·달성)을 소스로 적재한다.** 비율 지표의 분모가 된다
5. **`CRITICAL` 의 정의를 하나로 정한다.** 지금 `lane` 기준 1,106건과 `status` 기준 105건으로
   10.5배 갈리고, `lane=critical` 의 89%가 `UNVERIFIED` 다. 정의를 고르기 전에는 어느 숫자도 보고할 수 없다

## 8. 억지로 만들면 안 되는 것

**계산으로 만든 숫자는 원문 근거가 없다.**
단가·빈도를 가정해 곱한 값은 그럴듯해 보이지만 어느 자료에도 그 숫자가 없다.
WM 은 "근거 없는 숫자 0건"을 하드 게이트로 두고 있으므로,
가정 곱셈으로 만든 금액은 게이트를 통과시키려면 게이트를 약화시켜야 한다. 그렇게 하지 않는다.

정량화를 못 한다는 답이 **틀린 답보다 낫다.**
