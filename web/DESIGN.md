# WM Design System — 열람실(Reading Room)

> 오로라웍스 World Model 웹의 디자인 정본. 색·글자·간격·모션의 **단일 소스**다.
> 컴포넌트에서 임의의 hex·px·radius 를 만들지 않는다. 여기 있는 토큰만 쓴다.
>
> 관련: 제품 요구는 `docs/PRD.md` §14, 렌더러 경계는 `web/RENDERER-DECISION.md`.

---

## 0. 제품 이름과 한 줄 설명

| 자리 | 표기 |
| --- | --- |
| 사용자에게 보이는 이름 | **오로라웍스 World Model** (약칭 **WM**) |
| 한 줄 설명 | 회사가 아는 것과 그 근거가 어떻게 연결되는지 보여주는 지식 월드 |
| 코드·저장소·API | `business-world-model` / `bwm-*` 유지 (내부 식별자는 안 바꾼다) |

`BWM` 이라는 글자가 **화면에 보이면 결함**이다. 저장소 이름·환경변수·컨테이너 이름에는 남아 있어도 된다.

## 1. 디자인 방향: 열람실

WM 을 쓰는 사람이 하는 일은 **읽고, 따져 보고, 원본을 확인하는 것**이다. 대시보드를 보는 일이 아니다.
그래서 화면을 열람실로 짠다.

| 화면 | 열람실에서 무엇에 해당하나 | 표면의 성격 |
| --- | --- | --- |
| Ask 답변 | 사서가 정리해 준 **브리프** | 읽는 면. 흰 종이, 넓은 여백, 한 단 큰 본문 |
| Ask 그래프 | 그 브리프의 **출처 도면** | 도면 면. 한 단 눌러 앉힌 바탕, 격자, 얇은 선 |
| Library | **서가** | 목록 면 |
| Explore | **주제별 서랍** | 목록 + 상세 |
| Changes | **입고 기록** (이번에 무엇이 들어왔나) | 시간순 기록 면 |

**읽는 면과 조작하는 면은 글꼴이 아니라 종이색·여백·글자 크기·여백 각주로 갈라 놓는다.**
답변 본문은 15.5px 로 화면의 다른 글(14.5px)보다 한 단 크고, 줄 간격이 넓고, 한 줄 길이가 묶여 있다.
이것이 이 제품의 우선순위 ①(좋은 답)을 시각으로 못 박는 장치다.

> **2026-08-10 뒤집힌 결정: 답변 본문의 명조(Nanum Myeongjo)를 버렸다.**
> 원래는 "답변 본문만 명조"로 읽는 면을 갈라 놓으려 했다. 화면에서 실패했다.
> 나눔명조 한글은 획 대비가 낮아 16px 에서 얇고 흐릿하게 보이고, 라틴(`KB`·`GA`·`RFP`)만
> 세리프로 튀어 한 줄 안에서 두 글꼴처럼 읽힌다.
> **글꼴 로딩 문제가 아니었다.** CDP `CSS.getPlatformFontsForNode` 로 재니 본문 186자 전부가
> `NanumMyeongjo` 로 정상 렌더되고 있었는데도 "글씨체가 깨졌다"는 신고를 받았다.
> 크기를 17px 로 올리는 안도 렌더해 대조했지만 얇음이 남아서, 고딕 통일로 정했다.
> 그래서 `--font-read` 는 `--font-ui` 를 그대로 가리키고, `@fontsource/nanum-myeongjo`
> import 3개는 `src/main.tsx` 에서 뺐다.

### 시그니처: 여백 각주 (marginalia)

답변 본문 오른쪽에 여백 열을 두고, 각주가 달린 줄 옆에 **그 근거의 자료 이름**을 작게 적는다.

```
가나손해보험은 GA 카카오톡 소통채널 구축 사업의        ┊ ⁷ 영업활동일지
기술협상을 마쳤고 [7], 협상 단계 금액은              ┊   2026-07-14
2.85억으로 확인됩니다 [9].                          ┊ ⁹ BD Overview.xlsx
                                                   ┊   Deal!F12
```

- 읽으면서 "이 문장이 어디서 왔는지"가 **눈을 옮기지 않고** 보인다.
- 여백 각주를 누르면 그래프 강조 + 근거 서랍 + 원본 열기가 한 번에 걸린다.
- 근거를 카드 더미로 아래에 쌓지 않아도 된다. §3 의 "Evidence 가 박스로 끝없이 쌓임" 불만이 여기서 해소된다.
- 좁은 화면(< 1200px)에서는 여백 열이 접히고, 각주를 누를 때 근거가 시트로 올라온다.

**이것이 이 화면의 유일한 대담한 장치다.** 나머지는 조용하게 둔다.

## 2. 색

오로라웍스 제품군의 브랜드 색을 물려받는다(`app/aurorasuite-ui-workspace/DESIGN.md` `primary #5C60C0`).
WM 이 별개 도구가 아니라 오로라웍스 의 일부로 보여야 하기 때문이다. 그라데이션은 쓰지 않는다.

### 코어 6색

| 이름 | Light | Dark | 쓰는 곳 |
| --- | --- | --- | --- |
| `ink` | `#1A1C22` | `#E9EAF2` | 본문 글자 |
| `paper` | `#FFFFFF` | `#171922` | 읽는 면 (답변·상세) |
| `ground` | `#F1F2F6` | `#0F1117` | 앱 바탕 |
| `board` | `#E9EBF1` | `#131620` | 그래프 도면 바탕 (한 단 눌러 앉힌 면) |
| `indigo` | `#5C60C0` | `#9DA0D9` | 유일한 Primary Accent |
| `oxide` | `#B4342A` | `#F09189` | 놓치면 안 되는 항목 |

중성색은 순회색이 아니라 **indigo 쪽으로 살짝 기울인 회색**이다. 고른 색으로 읽히게 하려는 것이다.

### 전체 토큰

```
--wm-ink            #1A1C22   본문
--wm-ink-2          #565C6B   보조 설명
--wm-ink-3          #878D9C   메타데이터 (조용하게)
--wm-paper          #FFFFFF
--wm-paper-sunk     #F7F8FB   읽는 면 안의 눌린 블록(발췌 등)
--wm-ground         #F1F2F6
--wm-board          #E9EBF1
--wm-rail           #23244A   좌측 내비 (오로라웍스 sidebar 계열)
--wm-line           #DFE1EA   기본 구분선
--wm-line-soft      #EDEFF4   더 약한 구분선
--wm-line-strong    #C3C7D4   강조 구분선

--wm-accent         #5C60C0
--wm-accent-ink     #42459B   흰 배경 위 글자·링크용 (AA 통과)
--wm-accent-soft    #EEEFF9   선택된 행·칩 배경

--wm-critical       #B4342A   놓치면 안 되는 항목
```

`critical` `conflict` `verified` `unknown` 넷만 의미색이다. 나머지 어디에도 색으로 뜻을 싣지 않는다.
**색만으로 뜻을 전하지 않는다.** 넷 다 아이콘 또는 글자를 함께 붙인다.

### 그래프 팔레트 — 14색을 6계열로 줄인다

지금은 노드 종류마다 색이 하나씩 있어 무지개가 된다. 노드는 **중성 판(plate)** 으로 그리고,
왼쪽에 4px 세로 띠 + 아이콘 + 종류 글자로 구분한다. 띠 색은 6계열만 쓴다.

| 계열 | 노드 종류 | Light | Dark |
| --- | --- | --- | --- |
| 사업·시장 | BusinessDomain, Industry | `#5C60C0` | `#9DA0D9` |
| 고객·거래 | Account, Deal, Competitor | `#0E7A9E` | `#5FBEDD` |
| 요구 | Need | `#A8630C` | `#E0A45E` |
| 역량·기능·제품 | Capability, Feature, Product | `#0E7350` | `#4FC79E` |
| 근거·지식 | Claim, Observation, Evidence, Source | `#6B7280` | `#9AA1B0` |
| 사건·사람 | Event, Persona | `#7A5AA8` | `#B79FDA` |

## 3. 글자

CDN 을 쓰지 않고 npm 으로 받아 자체 호스팅한다. 사내망·오프라인 데모에서 글꼴이 조용히 바뀌면 안 된다.

| 역할 | 글꼴 | 근거 |
| --- | --- | --- |
| UI·라벨·그래프 | **Pretendard Variable** | 한글 제품 UI 의 표준. 자막 폭이 좁아 밀도 높은 화면에 맞는다 |
| 답변 본문 | **Pretendard Variable** (UI 와 같다) | 명조를 쓰다 버렸다. 위 「뒤집힌 결정」 참조 |
| 위치·ID·수치 | **JetBrains Mono** | `Deal!F12`, `p.30`, `slack:C087.../1772...` 를 흐트러지지 않게 |

> ui-ux-pro-max 는 이 제품에 "academia / library / scholarly" 계열과 Cormorant Garamond + Crimson Pro 를 추천했다.
> **방향(학술적 읽기)은 받고 글꼴은 버렸다.** 두 글꼴 다 한글 자막이 없어서 한국어 화면에서 무너진다.
> 한글 명조(나눔명조)로 대신해 봤지만 그것도 화면에서 무너졌다. **한국어 화면 본문에 세리프를 쓰지 않는다**가
> 이 제품에서 두 번 확인된 결론이다.

### 타입 스케일

| 토큰 | px | 줄높이 | 쓰는 곳 |
| --- | --- | --- | --- |
| `--fs-display` | 30 | 1.28 | Ask 초기 화면 제목 |
| `--fs-h1` | 22 | 1.35 | 페이지 제목 (Ask 의 질문은 여기서 빠졌다: 아래 §6) |
| `--fs-h2` | 17 | 1.4 | 섹션 제목, 결론 제목 |
| `--fs-lead` | **17** | **1.72** | **결론.** 화면에서 가장 큰 본문. 이 단락이 곧 답이다 |
| `--fs-read` | **15.5** | **1.75** | **답변 본문·핵심 주장.** UI 본문(14.5)보다 한 단 크게 |
| `--fs-body` | 14.5 | 1.6 | 일반 UI 본문 |
| `--fs-sm` | 13 | 1.5 | 보조 설명, 발췌 |
| `--fs-xs` | 12 | 1.45 | 메타데이터. **이보다 작은 글자는 쓰지 않는다** |
| `--fs-node` | 13 | 1.35 | 그래프 노드 라벨 |
| `--fs-node-type` | 11 | 1.2 | 그래프 노드 종류 (라벨 아님, 분류표) |

**11px 이하는 노드 종류 표기 한 곳만 허용한다.** 실측에서 노드 라벨이 11px 이었고, 그게 §3 의
"Node Label 을 읽기 어려움" 의 원인이다. 라벨은 13px 로 올린다.

답변 본문은 한 줄 **60~72자**를 지킨다(실측 42자 → 좁아서 눈이 자주 되돌아간다). `max-width: 46rem`.

## 4. 간격·모서리·선·그림자

```
--sp-1  4px    --sp-2  8px    --sp-3 12px    --sp-4 16px
--sp-5 24px    --sp-6 32px    --sp-7 48px    --sp-8 64px

--r-sm  6px    작은 칩·배지
--r-md  8px    버튼·입력·카드
--r-lg 12px    패널·시트
--r-full 999px 각주 번호(원형)

--shadow-1  0 1px 2px rgba(26,28,34,.05)                    올려 놓은 행
--shadow-2  0 2px 4px rgba(26,28,34,.06), 0 12px 28px rgba(26,28,34,.08)   서랍·모달
```

8px 배수만 쓴다. 4px 은 아이콘·글자 미세 정렬에만.

**선은 필요한 곳만.** 실측에서 border 를 그리는 요소가 283개였다. 목표는 **60개 이하**다.
- 카드로 감싸는 대신 **여백과 구분선 한 줄**로 나눈다.
- 같은 성격의 항목이 이어지면 항목마다 상자를 두르지 않고 **목록 안 구분선**으로 잇는다.

## 5. 모션

| 무엇 | 시간 | 이징 |
| --- | --- | --- |
| 호버·누름 | 120ms | `ease-out` |
| 상태 전환(강조·펼침) | 200ms | `cubic-bezier(.2,.8,.2,1)` |
| 서랍·시트 | 260ms 등장 / 180ms 퇴장 | 등장 `ease-out`, 퇴장 `ease-in` |
| 그래프 펼침 전체 | **≤ 1.8초** | 아래 표대로 |

### 그래프 펼침 순서 (요구 §8)

| 시각 | 나타나는 것 |
| --- | --- |
| 0.00s | 질문의 중심(focal) 노드 |
| 0.30s | 중심에서 나가는 **선** |
| 0.50s | 그 선이 닿는 노드 |
| 0.90s | 다음 단계의 선 + 노드 |
| 1.30s | 근거·자료 계열 노드 |
| 1.60~1.80s | 최종 상태. **이후 아무것도 움직이지 않는다** |

**선이 노드보다 먼저 그려진다.** 무엇에서 무엇으로 이어지는지가 그 순서로만 읽힌다.
`다시 보기` · `건너뛰기` 를 제공하고, `prefers-reduced-motion: reduce` 면 최종 상태를 바로 그린다.

금지: 3D, 계속 떠다니는 노드, particle, bounce, 장식 목적 애니메이션.

## 6. 정보 위계 — 무엇을 먼저 보여줄지

### Ask 답변 — 세 단 위계 (2026-08-10 개편)

화면을 열고 **10초 안에** 이 세 가지가 읽혀야 한다. 그 셋만 위에 두고 나머지는 전부 접는다.

```
① 결론          무엇을 말하고 싶은가       17px. 2~4문장. 배경 설명으로 시작하지 않는다
② 핵심 포인트     왜 그렇게 판단했는가       번호 + 제목 + 주장 1문장 + → 근거 1~2문장. 3~5개
③ 그래서 어떻게    무엇을 하면 되는가        추천 순서(화살표) + 다음 액션(목록)
────────────── 선 하나. 여기가 읽는 자리와 찾아보는 자리의 경계다
④ 상세 6줄       전부 접혀 있다            인용한 근거 / 불확실한 정보 / 아직 모르는 것 /
                                        추가 원문 근거 / 정리 전 답변 원문 / 분석 세부정보
```

**질문은 답이 아니라 맥락이다.** 그래서 22px 굵은 제목에서 14.5px `--ink-2` 로 내렸다.
위쪽 검색창에 같은 문장이 남아 있고, 그 줄은 브리프가 스크롤되는 동안에도 자리를 지킨다.

**위계는 크기와 여백으로만 만든다.** 세 단을 카드로 감싸거나 테두리를 두르지 않는다.
모두 같은 상자가 되면 셋이 대등해 보인다. 색으로도 나누지 않는다: 색은 각주와 경고에만 쓴다.
선은 상세 영역과의 경계 하나만 둔다.

**정보를 지운 것이 아니라 자리를 옮긴 것이다.** 제품 공백·자료끼리 어긋남·추정·모르는 것·
근거 전체·근거의 세기·검색 경로는 전부 ④ 안에 그대로 있다. 결론을 뒤집을 만한 것만
결론 위에 작은 배지로 남긴다: `⚠ 핵심 근거 부족`(근거 세기 LOW) · `⚠ 일부 추론 포함`(추정·주의).

**④ 분석 세부정보에 들어가는 것**: 근거의 세기(3칸 막대 + basis), Query Route(Q-E/Q-M/Q-S),
노드·엣지 수, 검토한 근거 수, 정리 결과(핵심 주장 몇 개 · 근거 검사에서 버린 주장 몇 개),
policy_version, query_id, answered_at, matched_rule.

**이 배치를 만드는 것은 화면이 아니라 서버다.** `POST /brief` 가 답변을 다시 배치해
`types/brief.ts` 구조로 돌려주고, 화면은 그 구조만 보고 그린다. LLM 이 쓴 문장 구조에
레이아웃이 기대지 않게 하려는 것이다. 정리기가 실패하면 `mode="raw"` 로 원문을 그대로 싣고
화면이 그 사실을 밝힌다. 자세히는 `api/distill.py`.

**정리는 답변보다 늦게 온다(실측: 캐시 없으면 114초, 캐시가 맞으면 0.2초).** 그동안 좌측은
대기 화면을 그대로 두고 여섯째 단계 「읽는 순서로 배치 중」을 켠다. **좌측을 두 번 그리지 않는다.**

처음에는 답변이 오는 즉시 원문을 띄우고 정리본이 오면 바꿔 끼웠다. 캐시가 맞을 때는 괜찮았지만
캐시가 없으면 1~2분 뒤에 읽고 있던 화면이 통째로 다른 구조로 바뀌어, 읽던 자리를 잃었다.
사용자 신고: 「핵심 포인트가 확실히 늦게 나와.」

기다리기 싫은 사람에게는 출구를 준다. 대기 화면의 [기다리지 않고 답변 원문 보기]를 누르면 원문이
나오고, 그 뒤 정리가 끝나도 **화면을 저절로 바꾸지 않는다.** 「정리가 끝났습니다 · 정리본 보기」
한 줄만 띄우고, 누를 때 바뀐다. 뒤바뀜은 사용자가 고를 때만 일어난다.

### 조용한 메타데이터

메타데이터는 `--wm-ink-3`, `--fs-xs`, 배경 없이 쓴다. 배지로 감싸지 않는다.
**배지는 상태에 뜻이 있을 때만 쓴다**(미검증 중요 항목, 자료끼리 어긋남, 그래프 잘림).
실측 배지 70개 → 목표 **화면당 6개 이하**.

## 8. Navigation / IA

```

  ▸ 묻기        Ask       기본 진입
  ▸ 둘러보기     Explore   Entity 중심

```

**Graph 는 메뉴가 아니다.** 네 화면을 관통하는 상호작용 층이다.

| 화면 | 그래프가 무엇을 그리나 |
| --- | --- |
| Ask | 이 답을 만든 관계 |
| Explore | 고른 Entity 주변 관계 |
| Library | 이 자료에서 나온 지식의 관계 |
| Changes | 이번 실행에서 새로 생긴 노드·관계 |

전체화면 그래프 모드는 어느 화면에서든 `⤢` 로 들어간다.
모든 화면은 URL 로 직접 열린다: `/ask?q=…` · `/explore/account/kb손보` · `/library/src_bd_overview` · `/changes/ingest`.

### 목록 화면 세 곳 개편 (2026-08-11)

**서재는 폴더 트리다.** 자료 270종을 평평한 목록 + 그룹 칩으로 두면 찾을 수 없다. 칩은 "지금
무엇으로 걸렀나"는 보여 주지만 "안에 무엇이 있나"는 보여 주지 못한다. 왼쪽에 `그룹 → 자료 종류`
두 단 트리를 두고 모든 가지에 개수를 적는다. 세 단으로 만들지 않는다 — 자료 자체는 오른쪽
목록이 받는다. 계층은 상자·색이 아니라 **들여쓰기와 굵기**로만 만든다. 트리 뼈대는 서버
집계(`facets.source_types[].group`)로 받아서 270종을 한 번에 내려받지 않는다.

**저장함은 두 묶음이다.** 「최근 질문」은 자동으로 쌓이고 7일이 지나면 사라진다. 「저장한 것」은
직접 담은 것이고 지울 때까지 남는다. 섞으면 담아 둔 것이 최근 질문에 밀려 내려간다. 오래된
것을 지우는 시점을 따로 잡지 않고 **읽을 때 거른다** — 화면을 열 때마다 거르면 7일 규칙이
저절로 지켜진다.

> 저장함은 화면만 있고 **담는 버튼이 어디에도 없었다.** 빈 화면이 "답이나 대상에서 담아
> 두면"이라고 안내했지만 그 버튼이 없었다. 답변·대상 상세·자료 상세 세 곳에 `SaveButton` 을
> 붙였다.

**변경은 무엇에 쓰는 화면인지 먼저 적는다.** `ingest` 라는 내부 이름 아래 `+ 노드 30,174` 만
늘어놓고 있었다. 숫자는 맞았지만 읽는 사람은 그게 많은 것인지, 자기가 무엇을 해야 하는지 알
수 없었다. `지금 무엇이 들어 있나` → `언제 무엇이 들어왔나`(실행별 한 문장) → `답하지 못하는 것`
순서로 놓고, 세부 숫자는 접는다. 새 자료를 읽은 실행과 이미 읽은 자료에서 더 뽑아낸 실행을
`source_count` 로 갈라 다른 문장으로 쓴다.

**시각에 시간대를 더하지 않는다.** 적재가 적어 준 시각에 `Z` 가 붙어 있지만 그것이 정말 UTC 인지
로컬 시각에 `Z` 를 붙인 것인지 알 수 없다. 확실하지 않은 값에 9시간을 더하면 틀린 시각을
자신 있게 보여 주는 셈이다. 적힌 값을 그대로 읽는다.

## 9. 원문으로 가는 길 (요구 §7)

### 위치는 두 가지고 둘은 다른 것이다 (2026-08-11 개편)

근거 서랍은 위치를 **한 덩어리로** 보여 주고 있었다. 그래서 화면에 뜬 경로가 지식 월드 쪽
위치인지 원본 파일 쪽 위치인지 알 수 없었다. 사용자 지적: 「비즈니스 모델 안의 위치와,
실제 소스의 위치는 달라. 둘 다 볼 수 있어야 해.」

이제 한 상자 안에서 얇은 선으로 세 칸을 가른다. 상자를 셋으로 늘리지 않는다.

| 칸 | 답하는 질문 | 담는 것 |
| --- | --- | --- |
| ① 지식 월드 안의 위치 | 이 근거가 무슨 지식을 만들었나 | 각주 번호 · 붙은 노드(자료 노드는 뺀다) |
| ② 자료 안의 위치 | 원본의 어디인가 | 자료명 · 시트·칸·쪽·메시지 · [WM 에서 펼쳐 보기] |
| ③ 원본 열기 | 실제 원본을 어떻게 여나 | 아래 표 |

### 원본을 여는 세 갈래

자료 270종은 **모두 로컬 경로**다(`canonical_location`). 자료 메타에 URL 필드가 아예 없어서
구글 드라이브 링크 같은 것은 만들 수 없다(짐작해서 만들지 않는다).

| 갈래 | 언제 | 무엇이 열리나 |
| --- | --- | --- |
| `slack` | locator 가 `slack:<channel>/<ts>` | `https://aurorasoftkr.slack.com/archives/<channel>/p<ts>` 새 탭 |
| `file` | 자료 경로가 등록돼 있다 | `POST /browse/open-source` → 이 컴퓨터의 기본 앱으로 실제 파일 |
| `none` | 둘 다 아니다 | **「원본 링크 없음」을 적고** 왜 못 여는지 + 경로 복사만 |

**깨진 링크를 만드는 것이 링크가 없는 것보다 나쁘다.** 브라우저가 열 수 없는 경로에 `열기`
버튼을 달지 않는다. `file://` 링크는 만들지 않는다(크롬이 스크립트로 열지 못하게 막아 놨다).

**슬랙 워크스페이스 주소와 채널 이름은 짐작하지 않고 덤프에서 읽었다.** 채널 ID
(`#C087J33P9PT`)를 화면에 그대로 내보내면 어느 대화인지 알 수 없어서, `gen-sources.mjs` 가
덤프 첫 줄의 `channel_name` 과 permalink 의 워크스페이스(`aurorasoftkr`)를 함께 굽는다.

### 파일 열기의 안전 장치

화면은 **자료 번호만** 보낸다. 경로는 서버가 그래프에서 읽는다. 사람이 보낸 문자열로 파일을
열면 그래프 밖의 어떤 파일이든 열리게 된다.

- 열람 제한 자료는 계정 권한을 먼저 본다(답변 경로와 같은 기준)
- 등록된 위치에 파일이 없으면 404 로 그 사실을 말한다
- 서버와 사람이 다른 컴퓨터에 있으면 뜻이 없다 → `BWM_ALLOW_OPEN_FILE=0` 으로 끈다

### 근거를 얼마나 믿을 수 있나 (2026-08-11 개편)

`T1` 배지와 5칸 막대만 있었다. 맥락을 아는 사람에게는 충분했지만 처음 보는 사람은 T1 이
좋은 쪽인지도 알 수 없었다. **판정 한 문장을 맨 앞에 놓고** 등급은 분모까지 적는다.

- 「믿을 만합니다」 · 「대체로 믿을 만합니다」 · 「참고할 만합니다」 · 「조심해서 보세요」 · 「확인이 필요합니다」
- 등급은 `5등급 중 1등급` 으로 적고 「1등급이 가장 믿을 만합니다」를 붙인다
- 판단축·정본 범위·글자를 읽은 방법·개인정보를 전부 사람 말로 쓴다(영어 enum 을 내보내지 않는다)
- 등급 자체는 지우지 않는다. 노드 크기에는 여전히 쓰지 않는다(PRD §14.4)

발췌가 420자를 넘으면 8줄로 접는다. 실측에서 발췌 하나가 911px 이었고 서랍 본문은 822px 라,
발췌가 화면을 다 먹으면 바로 아래 판정이 스크롤 밖으로 밀렸다.

## 10. 로딩·빈 화면·오류 (요구 §17)

로딩은 단계를 말한다. 스피너만 돌리지 않는다.

```
질문 이해 중  →  관련 대상 찾는 중  →  근거 모으는 중  →  관계 확인 중  →  답 정리 중
```

그래프도 같이 움직인다: `중심 준비` → `관계 구성` → `펼침`.
Q-S(전략 질문)는 1~3분까지 걸리므로 경과 시간과 "왜 오래 걸리는지"를 함께 적는다.

빈 화면은 **무엇을 할 수 있는지** 보여준다. 오류는 기술 문구 대신 **다음에 할 일**을 적는다.

| 여백 각주 | 10개 | 6개 (본문이 짧아진 만큼 줄었다) |
| 우측 그래프 노드 | 18 | **18** (건드리지 않았다) |
| 가로 스크롤 (1440·1280·1024·768·375) | 0건 | **0건** |
| console.error | 0건 | **0건** |

**할 일이 첫 화면에 안 들어온다(1082px).** 핵심 주장 5개가 그 위를 차지하기 때문이다.
주장을 3개로 줄이면 들어오지만, 「핵심 주장 3~5개」가 요구라서 그쪽을 지켰다.
한 번 스크롤로 닿는다.

**자 하나를 고쳐 잡았다.** 「답변 본문이 첫 화면에서 차지하는 비율」은 `.answer-text` 한
요소를 재고 있었다. 답변이 세 단으로 갈리면서 그 요소는 결론 하나만 덮게 됐고, 지표가
82% → 16% 로 떨어졌다. 화면은 오히려 답으로 더 꽉 찼는데 자가 그것을 못 봤다. 그래서
읽는 세 단(`.lead` · `.points` · `.doing`)을 합쳐 재도록 바꿨고 **목표(≥62%)는 그대로
뒀다**(`web/scripts/wm-tour.mjs`). 옛 자로 잰 값도 `answerLeadOnly` 로 함께 남긴다.

**그래프 면적 16.7% 는 이번 작업과 무관하다.** 우측 도면 코드는 한 줄도 건드리지 않았다
(`web/src/graph/**`·`graph.css` 무수정). 이 값은 **답에 따라 움직인다**: 같은 질문인데
인용이 13건이던 회차는 노드 라벨 총 745자, 10건인 회차는 715자였다(엣지 85 vs 89).
도면 면적은 라벨 폭을 따라가므로 회차마다 18.1% ↔ 16.7% 사이를 오간다.
한 회차 안에서 정리 전·후를 비교하면 노드 수는 **18 → 18 로 같다**(실측).

### 자 두 개를 고쳐 잡았다 (밝혀 둘 것)

**① 질문 영역.** 처음에는 첫 화면의 질문 블록을 재려 했다. 그런데 첫 화면은 질문이 주역이라
비율이 커도 결함이 아니다. 원래 결함은 **답변 화면에서** 질문 후보 219px 이 답변을 아래로
밀어낸 것이었다. 그래서 답변 화면의 질문줄(46px · 5%)을 잰다. 첫 화면의 추천 질문 블록은
38% 이고 여기에는 목표를 걸지 않는다.

**② 답변보다 위 배지.** 목표 0 은 분류·개수를 알리던 메타데이터 배지를 뜻했다. 남은 1개는
`미검증 중요 항목 포함` 으로, **뜻이 있는 상태**라 답변 위에 두는 것이 맞다. 그래서 목표를
"뜻 있는 것만" 으로 고쳐 적었다.

### 자를 네 개 더 고쳐 잡았다 (2026-08-11, 밝혀 둘 것)

화면 구조를 바꾸면 그 구조에 걸린 지표가 0 이나 엉뚱한 값을 낸다. 목표는 그대로 두고 **자만**
고쳤다. 지난 회차의 교훈(「지표가 요소 하나에 묶여 있으면 거짓 신호가 온다」)을 그대로 밟았다.

| 지표 | 옛 자 | 새 자 | 왜 |
| --- | --- | --- | --- |
| `drawerOpenButtons` | `.origin-actions .btn` | `.origin .btn` | 위치를 세 칸으로 갈라 `.origin-actions` 가 없어졌다 |
| `drawerHasAuthority` | `.tier-scale` | `.trust-scale` | 판정 문장을 앞세우며 이름이 바뀌었다 |
| `runCards` | `.run-card` | `.runstep` | 실행 카드를 타임라인으로 바꿨다. 재는 것(실행 수)은 같다 |
| `libraryFilters` | `.filter` | `.filter, .tree-row` | 그룹 칩을 폴더 트리로 바꿨다. 재는 것(자료를 좁힐 수단)은 같다 |

새로 잰 것: `drawerOriginParts`(위치 칸 3) · `changesHasWhy`(무엇에 쓰는 화면인지 한 줄) ·
`changesHasTotals`(지금 총계) · `libraryTreeFolders`(폴더 수).

### 자를 한 번 바꿨다 (밝혀 둘 것)

처음에 "답변 한 줄 글자 수 42 → 60~72" 로 적었다. 그 60~72 는 **라틴 글자 폭(0.5em)** 을
가정한 값이고, 답변은 한글이라 자막이 1em 에 가깝다. 같은 폭에 절반밖에 안 들어간다.
그 자로는 목표를 채우려면 본문 폭이 1,100px 이 되어야 하는데, 브리프가 화면의 44% 라는
요구(§5)와 함께 성립하지 않는다.

그래서 **자를 한글 기준(폭 ÷ 글자크기)으로 바꾸고 목표를 28~40자로 다시 잡았다.**
개선 전 값도 같은 자로 다시 재서 21자다. 옛 지표도 `tour.json` 에 함께 남긴다.

## 13. 응답 속도 (데모에서 실제로 기다리는 시간)

화면을 다 만든 뒤 재 보니 조회가 느렸다. 원인은 하나였다: **그래프에 인덱스가 하나도 없었다.**
`natural_key` 로 노드를 찾는 것이 조회의 대부분인데 매번 노드 3만 개를 훑었다.

`scripts/create_indexes.py` 로 인덱스 21개를 만들고, 자료별 집계처럼 전체 스캔이 필요한 값은
서버 기동 때 미리 만들어 둔다(`api/browse.py` 의 `warm*`).

| 조회 | 인덱스·예열 전 | 지금 |
| --- | --- | --- |
| 서재 목록 | 30.4초 | 0.36초 |
| 수집 실행 상세 | 43.5초 | 0.01초 |
| 고객사 목록 한 페이지 | 44.6초 | 0.45초 |
| 자료 상세 | 11.5초 | 0.43초 |
| 대상 상세 | 9.7초 | 0.44~2.2초 |
| 데이터 상태 | 4.9초 | 0.54초 |
| 둘러보기 첫 화면 | 8.0초 | 0.38초 |

인덱스는 **데이터를 바꾸지 않는다.** 같은 결과를 더 빨리 찾게만 한다. 되돌리려면
`scripts/create_indexes.py --drop` 이고, 지워도 데이터는 그대로다.

집계 예열은 **스냅샷 1회 수집**이라는 이 데모의 전제에 기댄다. 자료를 다시 넣으면
API 를 재시작해야 반영된다.
